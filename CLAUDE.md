# Unrect

## Status

This project is experimental, but both the substrate (`ISpace`, `Plane`, `Point`, the strategy/scan/landmark interfaces) and the projection layer (`Unrect.Projections`, one vocabulary — `ProjectionBuilders<TSpace>`) now have deliberate, review-hardened semantics pinned by `src/Unrect.Tests` (xUnit, 2,274 tests) and `src/Unrect.Analyzers.Tests` (18 tests). Run `dotnet test src/Unrect.sln`; keep it green. Gate builds with `dotnet build src/Unrect.sln -v q --no-incremental` — incremental builds silently skip analyzer diagnostics (xUnit analyzers etc.), so a plain build can report 0 warnings while warnings exist.

## Problem Domain

Unrect addresses a real-world problem common in financial institutions: hierarchical data stored in flat 2D structures (primarily Excel spreadsheets). These are not simple tabular datasets — they contain nested, heterogeneous regions that need to be parsed into structured objects.

A typical example is an IRR report with:
- A header section (title, date, generic report info)
- Repeating client blocks, one per client
- Within each client block, sub-sections like capital calls, fundings, etc.

Row-oriented parsers are the wrong tool for this. They devolve into stateful cursor logic and fragile index tracking. Unrect takes a different approach: declarative 2D spatial decomposition. You describe the shape of the data once, and the framework handles decomposing the grid along that shape and projecting each part to a typed object.

## Design Philosophy: Declarative, Not Imperative

This is the core design commitment of the project, and it constrains every API decision.

A user of Unrect **declares the shape** of the data — "a header, then N repeating client blocks, each containing a capital-calls section sized by this predicate" — as a static description built from shapes and strategies. The framework interprets that description to perform the decomposition. The user never writes traversal logic: no "current row" state, no manual index arithmetic, no loops that walk the grid deciding what comes next. (`LayoutCursor` is a cursor in name only: `Next` declares the next child in flow order and hands back what it read, and exposes no position to compute with; the lambda runs once at declaration, before any space exists, with each child reading as the empty value of its type, and once per application with the values.)

The distinction matters because the imperative alternative is the failure mode this project exists to escape. Row-oriented parsers force the shape of the data to live implicitly in control flow, where it is fragile and unreadable. In Unrect, the shape is a first-class value: a composition of shapes and strategies that can be inspected, reused, and reasoned about independently of any particular spreadsheet.

Practical implications for API design:

- **Projections describe; they do not execute.** Constructing a projection should be side-effect free. Decomposition happens when the description is applied to a space (`Map`/`Apply`), not while the description is being assembled.
- **Strategies are the escape hatch for dynamism — but they are still declarative.** Variable-sized regions are handled by declaring *how* a boundary is determined (a predicate, a size rule), not by the user imperatively scanning for it. If a use case seems to require the user to write cursor logic, the right fix is a new strategy or combinator, not an imperative API.
- **Mapping is projection, not parsing.** By the time map functions run, decomposition is complete. Map functions read from an extent handed to them; they never influence or perform boundary decisions. A layout lambda runs once at declaration, with each child reading as the empty value of its type, and once per application with the values (2026-09-19, replacing the two-lambda slot form of 2026-09-17), and the two runs must declare the same children: a shape that depends on a value is a fault the first time it runs. The one bounded place where a shape depends on data is the bind rung, `Table(headerRows, eachRow: captions => …)`, which builds its row projection from the header it read and says so through `Opacity`.
- **Evaluate new features against this test:** does it let the user *say what the data looks like*, or does it make them *say how to walk it*? The former belongs in Unrect; the latter is a design smell. A second lens on the same question: could a writer execute this declaration — could it produce the file as well as read it? Declarations run backward; opaque code does not.
- **Explicit dimensions are the exception, not the rule.** Almost every boundary should be discovered by a strategy (predicate-based sizes, skip-while offsets). Hard-coded offsets/sizes are acceptable only for structurally fixed regions — e.g., a report header whose shape is part of the format's definition. A hard-coded count that merely *happens* to match today's file (a gap of 2 blank rows, a table 4 columns wide) is a fragility bug waiting for the next export.

## Architecture

### Core Metaphor

A "space" answers four canonical questions about a coordinate grid: its extent, and whether/what a cell at a coordinate holds. A "plane" is a rectangular region of one space — the space, a root origin, and an area — and cutting one is arithmetic: a composed origin over the *same* space, never a second space object. A "point" is one cell of a plane, addressed in the space's own root coordinates. A declared shape decomposes a space into a hierarchy of planes and points, projecting each part to a typed value as it goes. Strategies determine boundaries (sizes, offsets, row/column counts) by reading planes and points rather than by wrapping a subspace.

All five library projects multi-target `netstandard2.0;netstandard2.1` (since 2026-09-05), so the packages install on .NET Framework 4.6.1+ as well as .NET Core/5+. `Unrect.Tests` is `net8.0` everywhere and `net8.0;net48` on Windows — the net48 leg cannot run on Linux, so an OS condition in its csproj keeps Linux CI at net8.0; a net48 portability regression therefore surfaces only on Windows (`dotnet test src/Unrect.Tests/Unrect.Tests.csproj -f net48`). `Unrect.Benchmarks` stays net8.0.

**No `#if` forks — one source, both targets.** netstandard2.1-only constructs are removed rather than branched on: no default interface members (a strategy's whole-region answer is defined on the static `Unrect.Core.Scans` as the fold of its scan — `GetOffset`/`GetSize`/`GetArea`/`SelectRows`/`SelectColumns` are extension methods, not interface members), no `System.HashCode` (Core hand-rolls its combine to keep the package dependency-free), no `HashSet<T>.TryGetValue`, no `Dictionary<K,V>(IEnumerable<KeyValuePair<K,V>>)`. The two polyfills (`CallerArgumentExpressionAttribute`, `IsExternalInit`) are unconditional because *neither* netstandard has the type; a net5.0+ target is what would force an `#if`. Consequence: DIMs are no longer a seam option — a DIM on a published Core interface would compile everywhere and fail at run time on .NET Framework, so adding a member to a published Core interface is a breaking change with no escape hatch; type-testing is the whole capability recipe. That is exactly why `Plane<TSpace>` and `Point<TSpace>` are structs rather than interfaces: adding a member to one is a struct addition, not a breaking change, where the same growth on `ISpace` would break every implementer. The "a whole region and a stream cannot disagree" guarantee is by construction: a strategy has one spelling of its rule, the scan, and the whole-region answer is the fold of it.

### Data Flow

```
Excel file / 2D array
    -> adapter normalizes to a backend's own cell vocabulary   ("lexing": backend values -> one vocabulary)
    -> ISpace                                                  (the text facet — Area, IsBlank, AsText — and, for a store with one, the value facet IValueSpace<TValue>)
    -> Plane<TSpace> / Point<TSpace>                            (the region and cell a declaration is handed)
    -> ProjectionBuilders<TSpace> + Strategies                  (declarative description)
    -> projection.Map(space)                                   (hierarchical decomposition and projection, fused)
    -> typed objects
```

### Key Abstractions

- **`ISpace` / `IValueSpace<TValue>` / `Plane<TSpace>` / `Point<TSpace>`** — `ISpace` is the text facet: `Area`, and `IsBlank`/`AsText` of a coordinate, root coordinates, bounds-checked with `OutOfBoundsException` on every member; a plain CSV is an `ISpace` and nothing more. `IValueSpace<TValue>` is the optional value facet — one member, `ValueAt` — whose type is the space's to choose; a sheet's is the `CellValue` sum type, and every question about a value lives on the value's type. `Plane<TSpace>` is the 2-D locator a projection is handed — a space, a root origin, an area; cutting one (`Slice`) is arithmetic over the same space, so decomposing a sheet into a hundred regions costs a hundred struct copies and no reads. `Point<TSpace>` is the 0-D locator a plane mints: one cell, addressed in root coordinates, a bare ADDRESS with every question an extension (`p.IsBlank()` beside `p.IsDouble()`), compared by *address* rather than by value (`a == b` asks whether `a` and `b` are the same place, never whether they say the same thing). Growing either locator is a struct addition, not a breaking interface change — which is why the surface grows there and not on `ISpace`.
- **`GridSpace<T>` / `IValueSpace<T>`** — the in-memory door for a homogeneous grid: `GridSpace.Create(int[,], isBlank:)`, `Create(double[,], isBlank:)`, `Create(string?[,])`, `Create(object?[,])` (heterogeneous, each value saying what its CLR type implies) and the general `Create<T>(values, isBlank:, asText:)`. A cell's value is read back with `Point<IValueSpace<T>>.Value()`; the grid has no held-text question, because whether a cell holds text is the value's kind, which a homogeneous grid does not have.
- **Strategies** — Pluggable functions that determine spatial boundaries, now over `Plane<ISpace>`/`Point<ISpace>`:
  - `ISizeStrategy` — computes a `Size` from available space
  - `IOffsetStrategy` / `IAreaStrategy` — adapted from `ISizeStrategy`
  - `IRowStrategy` / `IColumnStrategy` — predicate-based row/column selection
  - Blankness conveniences: `OffsetStrategies.SkipBlankRows()`/`SkipBlankColumns()`, `SizeStrategies.RowsWhileAnyValue()`, `RowStrategies.TakeRowsWhileAnyValue()`, `ColumnStrategies.TakeColumnsWhileAnyValue()`
  - Explicit counts: `RowStrategies.TakeRows(n)` / `ColumnStrategies.TakeColumns(n)` — these throw `OutOfBoundsException` rather than clamp, consistent with `ExplicitArea`
  - `SizeStrategies.RowsWhileAny(predicate)` / `RowsWhileAnyValue()` + `.ToAreaStrategy()` (width = full available width, height = leading rows in which at least one cell satisfies the predicate) — the preferred way to size a data region instead of explicit bounds or `MaxArea`
  - `OffsetStrategies.SkipRowsWhileAll(predicate)` / `SkipRowsWhileAny(predicate)` declare a vertical offset such as "skip however many leading rows are entirely blank"; `SkipBlankRows()` is the zero-argument form. These do their primary work as the shape layer's defaults (e.g. `Table`'s placement); direct usage is pinned in `src/Unrect.Tests/Strategies/OffsetStrategyTests.cs`
  - `…Saying`/`…Where`/`…WithCell` are the closed canonical matchers, over what a cell says; `RowContaining`/`ColumnContaining` are the value vocabulary's — the same whole-cell, trimmed, case-insensitive comparison against the text a cell HOLDS, so a numeric 2024 is not a row containing "2024"; `TakeRowsToText`/`TakeColumnsToText` are their row/column-strategy twins, in the same vocabulary
- **Projections (`Unrect.Projections`) — one vocabulary, `ProjectionBuilders<TSpace>`, and one mapping interface, `IProjectionDefinition<TSpace, TResult>`.** A file imports the vocabulary once, closed over the space every declaration in it is written against (`using static Unrect.Projections.ProjectionBuilders<Unrect.Spreadsheets.ICellSpace>;`), and every factory below that line is prefix-free. `projection.Map(space)` decomposes and projects in one call, and the projection is a reusable, thread-safe value safe to apply to many spaces at once.
  - **Leaves.** `Point()` and `AsText()` are the two canonical leaves, closed over the text facet. `Point()` yields the cell's own address (`Point<TSpace>`) — the leaf for a reading this vocabulary does not name: a backend's own point-extension answers the rest (`Record(r => r["Amount"].Decimal())`), and it is also what a reader hands to its own complaint about a cell. `AsText()` yields what the cell says, unconditionally — a number renders its digits, a date its ISO form, so it is *total* and `Choice(AsText(), …)` is a degenerate choice (a narrower leaf belongs first, not `AsText`, which cannot fail). `Range`/`Row`/`Column` (through `CellBlock`/`CellStrip`), `Caption`, `Field`/`Fields` hand back points, never values: `Fields(...)` yields `IReadOnlyDictionary<string, Point<TSpace>>`, `Table()` (the exploratory dictionary rung) yields rows of the same. The kinded leaves — `Text()`/`Double()`/`Date()`/`Boolean()`, and the converting `Decimal()`/`Integer()` — assert which case of the value a cell holds and ship with the backend that has one: `Unrect.Spreadsheets`, over `ICellSpace`, via `SheetProjectionBuilders<TSpace>`/`SpreadsheetProjectionBuilders<TSpace>`. `Caption`, `Heading` and `Field` match what a cell SAYS, whatever its kind — a caption that is a year matches "2024" — since structure is written in what a reader sees.
  - **The leaf firewall.** The kinded leaves are closed over `ICellSpace`'s reads (`Decimal()`/`Integer()` being the two named conversions over its double); there is no `Long()`, `Money()` or `Enum<T>()`, now or later — each would be a new failure vocabulary and a new writer obligation. A conversion beyond that set is `Select` territory. The firewall's target moved from `CellValue` (Core) to a backend's own kind set (`Unrect.Spreadsheets.Cell`), but the law is unchanged: nothing is added to `Unrect` to serve a leaf, and adding a backend accessor does not add one on its own.
  - **Kind vs conversion.** A kind failure speaks the document's vocabulary — `expected Number at B4, found Text` — never the reader's; a `Number` that will not fit the CLR type asked for is reported as a conversion on a number that is really there. The vehicle is `CellProblem` (a sentence awaiting an address) returned by a space's `TryGet…At` reads, thrown as `CellReadException` by the point-extension that calls one, caught by the calling primitive and rethrown as a `ProjectionException` with the declaration path and the cell's A1 — the same template a kinded leaf and the reflective table binder both go through (`CellReading` in `Unrect.Spreadsheets`), so a `Decimal()` leaf and a bound `decimal` column cannot describe the same cell differently.
  - **Read failures are located, not accumulated.** A location comes from the plane or point that a failing read was handed, never from an origin threaded down through the tree — `ProjectionContext` no longer accumulates one at all. Every lambda-calling primitive (`SelectDefinition`, `StripDefinition`, `BlockDefinition`, `RecordDefinition`, the two `Table` lambda rungs, the layout bodies) catches a `CellReadException` at the same one seam and rethrows through `ProjectionContext.Reading`.
  - **Layouts** — `VerticalFlow(v => new R(v.Next(x), v.Next(y)))`, `HorizontalFlow(...)`, `Overlay(...)`. One lambda, run twice: at declaration every `Next` records its child and hands back the empty value of its type (0, `""`, an empty list; `default` otherwise), so `Children` is complete and ordered with the use site on each edge and `Opacity` is null; per application every `Next` hands back its child's value and the lambda's result is the layout's. The lambda may assemble, count, join and format; one that reads a cell or reaches into an object nothing built is refused where it is written (read in the leaf; compute in `Select`), and one whose shape depends on a value is a fault. The reflective table binder, which builds a user's type, is the one layout with an internal door (`LayoutCursor.Recording`) to skip building it on the declaration pass. A null child or an empty layout is refused where it is written. A flow divides its extent into bands; an overlay hands every child the whole extent.
  - **Tables — one `Table` family across two packages.** In `Unrect`, over any `ISpace`: `Table(headerRows: 1, eachRow: captions => ...)` — **the bind** — reads the header once per application, hands its `LabelMap` to a lambda that returns the projection for one record, and applies that description per row; `Table(headerRows:, eachRow: someProjection)` — the composed row-slot rung, `VerticalBands` under a discovered header, wrapped as one `UnitDefinition` so its failure path (`Table[3] -> 'eachRow'`) is identical to a leaf's; `Table()` — every row as `IReadOnlyDictionary<string, Point<TSpace>>`, for sight-reading an unfamiliar sheet; `Table(row => ...)`/`Table(view => ...)` — the lambda escape hatches over `TableRow<TSpace>`/`TableView<TSpace>`. In `Unrect.Spreadsheets`, over `ICellSpace`: `Table<T>()`/`Table<T>(bind => ...)` — the reflective rungs, captions bound to a type's members by `CaptionComparer`, composed through the core bind rung by reflection (`RowBinding`/`MemberPlan`); a nullable member tolerates a blank and still fails on the wrong kind, and one member type asserts nothing at all — `Point<TSpace>` is filled with the labelled cell's address, the escape hatch for a column the six kinds do not describe. A table declares no offset of its own: it starts where anything else does, at the left edge of what it is handed, and the columns its header leaves blank before the first caption are columns of the table with no label (`ColumnStrategies.TakeTableColumns`, internal: the FIRST ROW alone settles that lead, so a value further down column A cannot move where the table begins). Reads by name are unaffected; an index — `r[3]`, `bind.Column(t => t.Amount, 3)` — is a position from the table's left edge, and a declaration that wants to count from the first caption says so (`SkipToFirstNonBlankCell()`, `Right(n)`). `bind.Column(member, index)` binds the column a caption cannot reach (a blank header cell, one of two identical captions); the dictionary rung gives a captionless column with nothing in it no entry and still refuses one that holds values. **A header may be several rows tall** (2026-09-20; `headerRows` is any count from zero up): the last row holds the captions and every row above it is a row of BANDS, and what the header yields is each column's PATH — the distinct regions it passes through top to bottom — a LIST of typed steps that is never joined into text and read back (`"From 2"` could be a band and a position, or a caption that says so). `HeaderRegions.Fold` is the one parse, a pure function over the header's words that asks a space only whether a cell is blank and what it says: a merged cell's text belongs to every cell it covers, and since the cells alone cannot say whether a blank was merged over or left empty the regions are reconstructed by the STATED convention every reader of such headers uses — a label claims the blanks beneath it (a tall label is its own column's name and spreads nowhere), else the blanks to its right, up to the next label, never past the region over it and never over a column with nothing beneath it (a spacer); the caption row never claims sideways, and a band never names a column with no caption. A wrong guess never reads a different cell. **A label is what a header cell SAYS, whatever its kind** — a row of years or period-end dates is a row of captions (a behaviour change: a numeric header cell used to be a column with no caption). A column is addressed by its path through one `params LabelStep[]` indexer on `TableRow` and `LabelMap` beside the exact `[int]`/`[string]` ones — a step is a name, the nth of a name `("Id", 1)` or a position `1`, EVERY number zero-based: `r["From", "Id"]`, `r["From", 1]`, `r[("Totals", 1), "Net"]` (a region is a label at one level that began at one column, so two bands that say the same thing are two regions). A one-step path is a NAME: the column whose whole path it is, before a caption somewhere under a band; `("Id", 0)` counts every column carrying the caption. FAIL FAST: a name several columns answer to is refused with the paths that say which — never the first — and every miss says what IS there; a path deeper than the header fails on the first row whatever the data is. `Table<T>(headerRows, bind, onBlank)` (and `LooseTable<T>`): **flat binding is the rule** — a member answers to a caption, or to the banded column whose WHOLE path run together is its name (`FromId` for `From, Id`; matching, never naming — a row still reads `r["From", "Id"]`, not `r["FromId"]`); one name, one column, so a caption and a run-together path that both answer are refused like any other two; `bind.Column(member, "From", "Id")` says which, and a path longer than the declared header is deep is refused where it is written. The scaffolder takes `headerRows` and writes that flat type from the table's own parse. A limit to know: a spacer column blank all the way DOWN ends the TABLE (its width rule is what lets two tables sit side by side), so the bands to its right are outside it — declare the width (`Sized(RowsWhileAnyValue()).Of(Table(2, …))`). Every rung accepts an `onBlank: BlankRowStrategy` (`Stop`/`Skip`/`Fault`/`Tolerate`) for a fully-blank body row; `Stop` (the default) is self-bounding, the others run to the enclosing edge.
  - **The default offset (2026-09-19).** A projection that does not say where it starts steps over the blank spans in front of it: a child of a flow or a repeat along its CONTAINER's axis (blank rows down a vertical one, blank columns across a horizontal one); the root and an overlay's children, which have no such axis, along the axis the run reads its source in (a column-major engine would skip blank columns there). Nothing moves across by default, and a declared anchor, distance or offset is taken at its word — `Down(1)` counts from exactly where the container put the child (`PlacementRules.DeclaresOffset` walks the wrapper chain; a node says what its children lead along through `DefinitionNode.LeadsChildren`, which its machine passes to `Start` and `CostReport` reads, so every `CostLine.Starts` says `Declared`/`AfterBlankRows`/`AfterBlankColumns`/`WhereItIsPut`). Tiler bands, a table's rows and a wrapper's inner start exactly where they are put. **A flow is a pattern and a strip is an index**: a flow divides a region into blocks with gaps of any size between them and a one-cell block is still a block, so a flow of leaves over a sparse row steps over the missing value; where a blank IS the value at a position, address by position (`Row(n, …)`, `Record`, an overlay with `Right(n)`, a table). Pinned by `DefaultOffsetTests`.
  - **Repetition and alternation** — `VerticalRepeat(item, separatedBy:, atLeast:)`/`HorizontalRepeat(...)`, `Choice`, `.Else`, `.Optional`. Every occurrence steps over the gap in front of it, so `separatedBy: BlankRows()` says nothing the default does not and `separatedBy:` is for a separator that is content; a repeat's next item that finds nothing but blanks is no next item, so a run ends quietly at a trailing blank band (a blank band is a gap, never a terminator — `.Until` ends a run at content). `VerticalBands(rows, each, onBlank:)`/`HorizontalBands(columns, ...)` is the tiler, not a repeat: a repeat repeats a *pattern* (each occurrence's extent discovered from the item), a tiler repeats a *fixed-dimension space* (a declared stride, nothing searched).
  - **Placement pipeline** — `On`/`Below`/`RightOf`/`OffsetBy`/`AfterBlankRows`/`AfterBlankColumns`/`SkipToFirstNonBlankCell`/`Down`/`Right`/`Until`/`UntilColumn`/`Heading`, entries on `ProjectionBuilders<TSpace>` that open a stage-typed pipeline (`On(mark).Down(1).Sized(...).Until(...).Heading(...).VerticalFlow(v => ...)`), plus the postfix twins on `IProjectionDefinition` in `ProjectionExtensions` (`.On`/`.Below`/`.RightOf`/`.OffsetBy`/…). Both spellings replay onto the same `Steps`; a contradiction (a second anchor, a second bound) is unspellable at compile time in the pipeline and refused at construction postfix. `.Named`, `.AsUnit(name)` (a composed rung's own unit label), `.AsScaffolding()` (marks a factory's internal plumbing so it folds out of a rendered path), `.Sized`, `.Padded`, `.Under(captions)` round out the modifiers.
  - **Matchers, rules and their lifts — the typed phantoms.** `RowWhere`/`RowWithCell`/`RowContaining`/`RowSaying` and the column twins, and every predicate-driven rule beside them (`RowsWhileAny`, `TakeRowsWhile`/`…To`/`…WhileAll`/`…WhileAny`, the `TakeColumns…` twins, `SkipRows/ColumnsWhileAll/Any`, `SelectSize`/`SelectArea`/`SelectOffset`, `RowsThenColumns`/`ColumnsThenRows`), read `Plane<TSpace>`/`Point<TSpace>` over the file's own space. **A canonical predicate asks the four questions; anything about kind or value is a typed predicate and names its space.** A matcher only locates and reports absence; `.On`/`.Below`/`.RightOf`/`.Until` decide what absence means. The demand rides in the return type through seven phantom interfaces — `IRowLandmark<TSpace>`/`IColumnLandmark<TSpace>` (unwrapped by `Landmark`) and `ISizeStrategy<TSpace>`/`IOffsetStrategy<TSpace>`/`IAreaStrategy<TSpace>`/`IRowStrategy<TSpace>`/`IColumnStrategy<TSpace>` (unwrapped by `Strategy`), none of them deriving from the plain form, all of them `in TSpace` so a rule built at `ISpace` flows into every file. Every member that takes one is doubled, so the demand is inferred with nothing annotated (`Sized(RowsWhileAny(p => p.IsDouble()))`, `On(RowWithFormula())`), and the lift unwraps once at construction — the engine receives the calculus's own object, never a wrapper, so the scan the engine gets is the rule's own. A rule unwrapped into the wrong space faults with `InvalidCastException`, which no tolerance boundary absorbs.
  - **Naming** — a child's path segment is the first of: its own `.Named`; the bare identifier it was written as at the capture site; otherwise its kind and 1-based position. Unchanged.
  - **`.Until(landmark)`** — unchanged: ends a shape's extent just before a content landmark, consuming the bound in full.

  Placement is applied by the engine's placement machine alone, exactly once, at every level including the root. Failures throw `ProjectionException` with the declaration path and an A1 cell location. `docs/vocabulary.md` is the complete operator survey. `CostReport.Of(definition)` is the dry run: per node, streams or holds and why.
- **Streaming (`Workbook`, in `Unrect.Spreadsheets`) — the second door onto a spreadsheet.** `Workbook.Open(path)` owns every cursor it opens and one string table; `book.Sheet(name)` is one forward pass over the sheet's own cursor — the engine drives it a row at a time and releases every row no open machine may still read, a cell read directly is loaded on the way to it, and a cell of a released row is a located read failure that says to read it inside the projection — and a FAULT, since it says nothing about the data (`CellReadException.IsFault`), so no tolerance boundary can report it as an absent section. Each call is a fresh pass; ask again to read again. The cost model is declaration-shaped: a table read one band per row holds a handful of rows, a shape that reads its extent whole holds its extent, and `CostReport` says which before a file is opened (see `docs/streaming.md`). **The cap:** `WorkbookOptions.BufferRows` is the most rows a pass may hold; exceeding it is a fault naming the innermost holder, never a degraded read. `Workbook.Statistics(sheet)` reports rows read, the peak held, the cap and the rows a survey took. **IO errors are faults, never tolerance** — a disk failure or a read after `Dispose` is classified a fault at every site that can absorb a foreign exception, so `.Optional()`/`.Else()`/`Choice` can never report a broken file as an absent section. User guide: `docs/streaming.md`.

## Known Bugs

- **A Strict-mode ISO date cell lexes as Text** (found 2026-09-22, low priority). A cell the file tags `t="d"` with an ISO 8601 value comes back from ExcelDataReader as the string, so it lexes as `Text` and `Date()` fails on it with `expected Date, found Text` — loud, and wrong. Only a workbook saved as "Strict Open XML Spreadsheet" carries such cells (Excel 2007 could not read the tag, so the default format still writes serials and almost no third-party writer uses it). The fix is the adapter's — a `d` cell is Temporal — if the reader exposes the tag at all; unexamined.

**What an `.xlsx` actually guarantees, for the record** (2026-09-22). The cell type tag is number, string (shared, inline, or a formula's text result; rich-text runs are still one string), boolean, error (a fixed vocabulary, newer ones included), or absent — blank. Every number is a double. A DATE is a number whose number format displays as one — built-in formats 14–22 and 45–47 and the CJK variants, or a custom format whose code carries date tokens outside quoted literals and brackets — which is deterministic, and is Excel's own and only notion of a date (`ISNUMBER` of a date is true): if Excel would show it as a date, we read it as a date; `[h]:mm:ss` is a duration and lexes as a number of days. So: Text/Number/Boolean/Error/Blank from the tag, Temporal from the format, and nothing else — formulas, hyperlinks, comments, merges and formatting are ASPECTS held in other parts, and the modern rich-value types (Stocks, Geography, images in cells) are references with a fallback, unexamined here. **A format is presentation and never a type, with dates the one LOSSLESS exception:** a date format reinterprets the number exactly, both ways; a decimal-places format ROUNDS for display, so a cell holding 2.7 shown as 3 is still 2.7, and "integer" is a fact about the stored value (whole, and fits), never about the format. (A workbook with "Set precision as displayed" has had its stored values rounded already, so the value rule is right there too.) `AsText` renders the VALUE, not what Excel displays: that 2.7 says "2.7". Edges that are not flaws: a serial under a General format is a number (Excel shows one too); a date typed or exported as TEXT is text, which is the one met in practice (`Text().Select(DateTime.Parse)`). Unverified, to pin with tests: the 1904 date system flag; the double-to-decimal rounding. An idea, not a plan: the number format is good evidence for the SCAFFOLDER (`0.00` argues `decimal` however whole the samples; `0` argues a count) — a guess a human corrects, which is where a guess belongs — and would want the format exposed beside font and fill.

~~**Elapsed-time cells throw.**~~ **Fixed.** A cell with an elapsed-time number format (`[h]:mm:ss` — built-in `numFmt` id 46, id 79, or any custom bracketed `[h]`/`[m]`/`[s]` format) now lexes as a `Number` of days (`TimeSpan.TotalDays`) rather than throwing — exactly the interim the Duration-kind question below always recommended. Pinned by `src/Unrect.Tests/Spreadsheets/SpreadsheetSpaceDurationTests.cs`.

## Design Direction

The forward design: a canonical coordinate substrate in Core (`ISpace`/`Plane`/`Point`, adapter-agnostic — spaces as "lexers" adapting backends into whatever vocabulary they need, with only the four canonical questions promised to everything above them), a backend-owned kind vocabulary for the formats that have one (`Unrect.Spreadsheets.Cell`), a document-level shape vocabulary (`Table`, `Repeat`/separator, `Choice`) built on the strategy calculus, capability seams for backend extras (formulas today, formatting next) under the rule that nothing in Core may require a capability, and an observability roadmap (named regions, decomposition trace, dry-run renderer, unconsumed-space warnings). New API work is checked against these principles. What is built and what remains is in **Where Work Left Off**.

## Open Design Questions

- **Strategy layering** — `IAreaStrategy` and `ISizeStrategy` are now identical in shape (both `Begin(Orientation) → ISizeScan`); `IOffsetStrategy` is a size scan read as an offset. Collapsing `IAreaStrategy` into `ISizeStrategy` (77 library references, 28 in tests; `Placement.Area` becomes `ISizeStrategy?`; the `AreaStrategy` wrapper, `ToAreaStrategy`, `Scans.GetArea`, the area phantom and `AreaStrategies` go) was proposed by the 2026-09-19 review and awaits discussion with the owner, as does the fold-versus-driver heuristic in `Scanning.RowMajorColumns`. Adjacent and DECIDED (owner, 2026-09-02, pre-publish): `Area` stays a distinct `Size` wrapper and keeps both its `Size` property and the `Width`/`Height` passthroughs — the two-spellings wart is confined to engine plumbing that library consumers never operate at, so it does not justify surgery on `ISpace`/`Placement`/the strategy interfaces. Revisit only if the strategy-layering question itself is ever taken up.
- **`IsText` was the wrong SHAPE — examined 2026-09-20/22, and BUILT 2026-09-21/22 on `feature/faithful-spaces`** (owner: "knock this out entirely"). **What stands:** `ISpace` is `Area`·`IsBlank`·`AsText`·`TryGetTextAt`; `CellProblem` is a two-string struct in Core with the floor sentence; `IsText`/`TryGetText` are derived on `Point`; one `Text()` leaf and one `point.Text()` in the core vocabulary; `ICellSpace` (renamed) holds `TryGetDoubleAt`/`TryGetDateTimeAt`/`TryGetBooleanAt`/`TryGetErrorAt`; `Decimal()`/`Integer()` are conversions over the double, shared by reads, leaves and binder, quoting the number as the cell SAYS it (1.50, not 1.5); `KindAt`/`Kind()`/`Describe`/`IsErrorAt` are gone and the `Is…()` forms are derived; `IFormulaSpace.TryGetFormulaAt` with `HasFormula()`/`Formula()`. Every existing failure sentence is byte-identical, which was the check. **Where the build differs from the record below, and what is left:** a bound `decimal`/`int` member fails with the SAME sentence a `Decimal()` leaf gives (the member is named by the PATH, `column 'Amount'`) rather than a new member-naming sentence — the leaf/column identity law is pinned by tests and was KEPT, and that is decided (owner, 2026-09-21: no strong view, followed the recommendation): the sentence already says what went wrong and quotes the value, the subject and path name the member, and a failure reading the same wherever it is met has earned its keep; the only thing a binder-own sentence would add is the CLR type, for someone who sees `Problem` without its path — revisit if that reader turns up; `Cell` still keeps an exact decimal for a fixture built from one (`Cell.Of(1.50m)`), now reachable only through `AsText` (its unused `TryGetDecimal`/`GetDecimal`/`TryGetInt`/`GetInt` were cut; what `Cell` should BE is the flagged redesign below); a read of a RELEASED row throws from inside the read (it never returns false, so `IsDouble()` on a row that has gone is refused, never answered no — pinned) and is now a FAULT (owner: "Optional absorbing it just hides a failure") — `CellReadException.IsFault`, set by the streamed sheet, carried through `ProjectorScope.Reading` and `EngineRules.IsFault`, so no tolerance absorbs it; before, `.Optional()` over a spent pass answered null (a boundary holds the rows of its own attempt, so a late read INSIDE one simply succeeds — what reaches a boundary is rows released before it began); `IValueSpace<T>.ValueAt` was left as it is (total, no try — a homogeneous grid has one reading and no refusal to word); the tests keep a test-only observer (`SpaceQuestions.KindAt`/`Describe`, derived from the reads) because a lexer test wants one word per cell. NOT done, awaiting names: the door renames (`Create`/`CreateWithFormulas`), `SheetProjectionBuilders`, and no package split. The record of how it was reached follows.
  - **WHERE IT LANDED (owner, 2026-09-22, "I more or less went completely full circle").** Three days of alternatives — `AreEqual`, `Holds<T>`, `IsTrue`, `IsKind<T>`, facet keys — tested the existing layering from every side, and it stood: **the space interfaces are the contract and the point extensions are sugar over them**, which is already how every read is built (`ICellSpace.TextAt/DecimalAt/…(out value, out CellProblem?)` with `p.Text()`/`p.Decimal()` wrapping them; `IFormulaSpace.FormulaAt`; `IStyleSpace.FontAt`/`FillAt`). What the circle produced is a CONVENTION and a model, none of it built:
    - **The model of a cell.** A cell has a VALUE — which has exactly one KIND (the tag of a closed union, the backend's own business) and several READINGS (a number answers decimal, double and sometimes integer; everything answers `AsText`) — and it has other ASPECTS that are not kinds of value at all: a formula is a SECOND STRING, its formatting is always there, later whether it is merged. Aspects are interfaces (`IFormulaSpace`, `IStyleSpace`); kind is one tag; readings are many. That is the facet discussion said in plain terms, and it is why facets are shelved.
    - **The convention: one `TryGet…At` per reading, and everything else derived.** On the space, `bool TryGetTextAt(int column, int row, out string value, out CellProblem? problem)` — the value, or the reason it could not be had. Derived ONCE for every space, as point extensions that cannot disagree with it: `point.TryGetText(out value, out problem)`, `point.IsText()` (true exactly when `Text()` would succeed — NOT a default interface body, which netstandard2.0 has not got), and the asserting `point.Text()` that throws the located failure. `Is…` asks about a READING (`IsInteger` on 1.5 is false, `IsDouble` true). A formula's absence is not a failure, so its pair is `TryGetFormulaAt`/`HasFormula` without a problem; font and fill are total and need no `Try`.
    - **The space takes coordinates; the point is what everyone else holds.** Measured: nothing above Core calls a space with raw coordinates — strategies, scans, the engine, the views, the binder and the header parse all hold a `Plane` and mint a `Point` — except the point extensions, whose whole job is that forwarding. So the space's interface is what an IMPLEMENTER writes (a grid and two integers, the cheapest hot path there is) and the point is the API; a space method taking a `Point` would say the space twice, invite a point from another sheet, and trip on `Point<ICellSpace>` not being a `Point<ISpace>`. The `…At` suffix already means "takes coordinates" (`KindAt`/`Kind()`, `FontAt`/`Font()`). (The substrate is, in the code, planes and points: `Line<TSpace>` was conceived as the locator with one coordinate fixed, addressed by ONE index — the job `CellStrip` does — and was never built.)
    - **On `ISpace`:** `TryGetTextAt` joins, `IsText` LEAVES the interface (derivable; every `ISpace` member is one every space must write) and `AsText()` becomes the `ToString()` of Unrect — what a cell SAYS, total, a rendering and nothing else — leaving `Area` · `IsBlank` · `AsText` · `TryGetTextAt`. Because the SPACE words the problem, the text read is declared once and INHERITED by the cell space, so there is one `Text()` extension and one `Text()` leaf, in the core vocabulary, each with the best sentence its space can give (`expected Text at B4, found Number` from a sheet) — which dissolves the two-`Text()` ambiguity that would otherwise forbid a core one. The price: `CellProblem` moves down to Core, which the charter permits (a contract speaks it); check what it drags first.
    - **THE OWNER'S SUMMARY (2026-09-22), which is the conclusion:** what we have is mostly correct; the naming convention wants to be explicit `TryGet…`; each `TryGet…` IS a "facet" and no facet TYPE is needed — a key existed to tell two things of one type apart, and a method's NAME already does (`TryGetText` and `TryGetFormula` both hand back a string and nobody can confuse them: the method is the facet, its name the key, the interface it lives on the demand); and **`KindAt` deserves a place nowhere.** Measured: the interface member is declared once, implemented in one line, called once (by the `p.Kind()` extension), and `p.Kind()` is called by NOTHING in the library and no example — the binder, the leaves, the failure sentences, the header parse and the scaffolder all go through the reads (what looks like a dozen call sites is `cell.Kind`, the TAG on the backend's own value struct, which is internal plumbing, how a sheet words `found Number`, and stays). Every kind test has a reading-level spelling — `IsText()`, `IsDouble()` for a number, `IsDate()`, `IsBoolean()`, `IsError()`, `IsBlank` — so `KindAt` is `IsText` over again: a member that restates what the reads already say. It leaves the interface and gets no derived `Kind()` either: there is NO SUCH THING AS AN EXHAUSTIVE SWITCH over a point, because a point can be several things at once (a number that reads as a double and as a decimal and says "42"; a value that also has a formula) — "which one of a closed set is it" is the wrong question, the honest general form would be a LIST of what a point can be, and the owner has no interest in Unrect implementing that. `IsErrorAt` and `Describe` go the same way (below), so the typed-cell contract is its `TryGet…At` reads and the error text, none a summary of another — which also answers "what if another space wanted `KindAt`?": it never has to write one. **The space is responsible for what it supports** (owner): which readings exist, which of them succeed for which cells, whether a number can be had as a double and not as a decimal, whether there is a NaN — all of it is the backend's to decide and the consumer gets what the space offers. "Is it a number" is not a guarantee the library makes, because "number" is not the library's concept; `IsDouble` belongs to the spreadsheet space, which is where it says what an Excel number is (a numeric cell in an `.xlsx` IS a double — dates are doubles with a format, integers and decimals are conversions — so the double read succeeds for every number there and the narrower ones may refuse).
    - **THE CONTRACT IS `TryGet…At` AND NOTHING ELSE; `Is…` IS DERIVED (owner, 2026-09-22).** Weighed: putting `Is…At` on the contract too, so a store that can say what a cell is without producing it skips a hop. Refused, for three reasons. The two halves CANNOT DISAGREE when one is defined as the other — three days went into removing a member that existed only to qualify another, and a contract with both `IsText` and `TryGetTextAt` rebuilds it. Every reading costs an implementer ONE method, not two, with no default bodies to soften it. And it is the choice that can be undone: with no default interface methods, adding a member to a published contract later breaks every implementer, so starting small keeps the fast path reachable and starting with both commits everyone for good. The hop itself is nothing for the stores we have (a tag check and a reference that is already there). What DOES cost is the failure path: a failed read builds its reason as `problem = at => $"expected {expected} at {at}, found {…}"`, a closure — an object and a delegate allocated on every miss, whether or not anyone reads the sentence — so a derived `IsText()` in `RowsWhileAny(p => p.IsText())` over a million non-text cells is a million allocations. TO FIX, and fixable without touching the contract's shape: make the problem a small struct (expected kind, found cell) that formats only when rendered; worth doing on its own, since every `…OrBlank` read and the binder take the same path, and the `IsText` reshaping cannot be judged fairly until it is. If a store ever really can answer "is it X" far more cheaply than it can produce X (lazily decoded text, a remote source), the library's own recipe applies: an OPTIONAL capability the derived `Is…` type-tests (`p.Space is IFastKinds fast ? fast.IsTextAt(…) : p.Space.TryGetTextAt(…, out _, out _)`), which is non-breaking to add later and which none of our stores would use today.
    - **`Describe` HAS ALL THE SAME ISSUES `KindAt` HAD (owner) and leaves with it.** It is `KindAt` wearing a string: the word after "found" (`Number`, `Text`, or an error spelled out). The interface member has one caller, the `p.Describe()` extension, which nothing in the library calls (2 tests, 3 lines of `edge-cases.linq`); the failure sentences do NOT go through it — they call an internal helper on the backend's own `Cell` while building a `CellProblem`, which is the backend wording its own failures and stays. The deeper reason is the facet problem: "what IS this cell" has no single answer, because a point is a value AND perhaps a formula AND a font AND a fill, and a free-floating `Describe` must pick one of those to talk about without saying which. A description only means something RELATIVE TO THE FACET THAT WAS ASKED FOR, which is exactly what the `problem` handed back by a `TryGet…` is: ask for text and fail, and the reason is about the value; ask for a formula and find none, and the reason is about the formula; ask for the font, which cannot fail, and there is nothing to say. So it is not promoted to `ISpace` either: nothing generic needs it (core diagnostics cite what a cell SAYS, or where it is), and every space would have to answer a question an integer grid has no answer to. A reader composing their own complaint has two honest sources, both well-defined — what the cell says (`AsText`, already the `ToString` of diagnostics) and why a PARTICULAR read failed (that read's `problem`, which they name because there is no "the" problem of a cell).
    - **DIAGNOSTICS LOSE NOTHING: a read words its own failure, about the thing it was asked for.** `found Number` was never the library classifying a point — it is the SPACE explaining why ITS read failed, from the tag it is holding at that moment — and that survives `Describe` and `KindAt` leaving: `TryGetTextAt` on a cell holding 42 hands back `expected Text, found Number`, and the generic layer carries it and adds the address and the declaration path, as now. What changes is only who may ask: there is no free-standing "describe this point", a description arrives WITH a specific failed read and is about THAT facet. So a value read (text, double, date, boolean) says the value was not that kind; a conversion (`Decimal`, `Integer`) says the number would not fit, quoting it; a FORMULA read says the cell has no formula — `expected a formula at B4; the cell has none (it says '42')`, and never `found Number`, which would be answering a formula question in value vocabulary: the formula read lives on `IFormulaSpace` and words its own failures, the value reads word theirs with the backend's internal helper, and with `Describe` off the contract there is no shared "what is this cell" for one to borrow from the other (a missing formula is usually not a failure at all: `TryGetFormulaAt` returns false and `HasFormula()` is derived; the sentence exists only for something that asserts one). Font and fill cannot fail. **The floor:** a space MAY hand back a problem and a good one should; where it hands back none, the library's asserting read writes one from the two things every space can always say — `expected Text at B4; the cell says '42'`, or `…; the cell is blank` — so a minimal new backend has acceptable diagnostics for nothing and can improve them later. `(it says '…')` is neutral context, what a person opening the workbook would see, and claims nothing about what the cell is.
    - **Left for the implementation to meet, none of them design:** what `CellProblem` drags with it into Core (and its change from a closure to a struct, done in the same pass); blanks — a `TryGet…` on a blank cell is false with "the cell is blank", and the `…OrBlank` reads and nullable members are derived from that; problems that are NOT about kind — a cell of a released row on a streamed sheet fails for a reason about the source, which the `problem` channel must still carry and which must stay a fault no tolerance absorbs; `IValueSpace<T>.ValueAt`, total for a non-blank cell, checked against the convention on purpose rather than left an exception by accident. Order when it is done: the allocation fix (small, independent, worth having anyway); `TryGetTextAt` on `ISpace`; the typed-cell contract; the binder's conversions — each gated by the existing tests.
    - **BE FAITHFUL TO THE STORE (owner, 2026-09-22): "it shouldn't belong on the space, that is lying about what the space does."** A space's interface lists what its store HOLDS, never what a consumer would like it to hold. An `.xlsx` cell's type tag is one of number, string, boolean, error, or absent (blank) — and EVERY number is an IEEE double: there is no integer, decimal, currency or percentage in the file, those are number FORMATS. So `DecimalAt` and `IntegerAt` claim a representation the store has not got and LEAVE the spreadsheet space's contract, which keeps text, double, date, boolean and the error text. The three layers, each with its own job: the SPACE tells the truth about the store (`TryGetDoubleAt`); the leaves and point reads read a cell as what it is (`Double()`) — and by the leaf firewall's own words ("a conversion beyond that set is `Select` territory") `Decimal()` and `Integer()` were conversions that got in before the rule was applied to them; the BINDER is a mapper, and converting between what a store holds and what a type wants is what a mapper is for (nobody thinks a mapper that fills a `decimal` property from a `float` column is lying about the database) — so `decimal Amount` in a bound record is the consumer's wish, met by the binder converting the double and failing as a CONVERSION (`the number 2.7 will not fit Transfer.FromId (int)`), which the kind-versus-conversion vocabulary already separates. `p.Decimal()`/`p.Integer()` may stay as CONVENIENCE EXTENSIONS over `Double()` — named conversions outside the space's contract, for the hand-written row that is already doing its own mapping. The conversion earns its keep wherever it lives: an Excel amount is a double and carries binary noise (0.1 + 0.2 is stored as 0.30000000000000004), and the double-to-decimal conversion rounds to the digits a double carries, so for money the decimal is the RIGHT answer — pin that with a test. A backend that genuinely holds decimals exposes a decimal read on its own interface, faithfully: the same principle.
    - **Where the typed-cell contract LIVES** is the real oddity, and is separate: the interface once called `ISheetCells` has nothing to do with spreadsheets — it is "a space of typed cells", which the rename to `ICellSpace` (the owner's, done) makes visible. A second backend with the SAME kinds (a CSV with inference, a database grid, an HTML table) should implement it and inherit the readings, the kinded leaves, `Table<T>` and the scaffolder; today it would have to reference the Excel package and ExcelDataReader to do so. So the contract and what is built on it want their own package (`Unrect.Cells`?) with `Unrect.Spreadsheets` keeping only what is Excel's — the door, `Workbook`, formulas, formatting, merges — the day a second kinded backend is real and not before (a split is cheap late and annoying to undo). A backend with DIFFERENT kinds has its own interface, as the charter says.
    - **The change list as it was written before the build:** `TryGetTextAt` on `ISpace` with `CellProblem` in Core; `IsText` off the interface; the cell reads renamed `TryGet…At` and cut to what the store holds (`DecimalAt`/`IntegerAt` become convenience extensions over the double, and the binder converts); the derived `Is…` forms; `Text()` read and leaf into the core vocabulary; `ISheetCells` → `ICellSpace` with the door renames. Wide and mechanical, and the existing tests are the check that nothing else moved. FACETS ARE SHELVED — explored below, not a plan. What follows is the record of how this was reached.
  - **(1) The odd pair on `ISpace` — small, local.** `AsText` means two things: a text cell's own VALUE, and a rendering of everything else (a number's digits, a date's ISO form). `IsText` exists only to say which of the two the caller just got — one member that qualifies another, and two calls to ask one question. It is NOT duplicative of the predicate mechanism: a predicate is a function anyone calls (`RowWithCell(p => …)`, `RowsWhileAny(p => …)` — the general "ask a cell anything", already shipped, which is how red text, numeric years and formulas are matched, each compiling only over a space that can answer), and what a space contributes is the QUESTIONS a predicate may ask. Over a sheet `IsText` duplicates `p.Kind() == CellKind.Text`; over a bare `ISpace` it is the one bit of kind the generic layer has, and it exists so the three text conveniences (`RowContaining`/`ColumnContaining`, `Caption`, `Field` — sugar for "this cell's value is this text, trimmed, ignoring case") can be written ONCE for every space (`CellMatching`'s guard; `Field`'s wording and the scaffolder's label-row search are incidental, and the header parse stopped using it when a label became whatever a header cell says). The better shape, if it is ever taken up: split the two meanings and drop the qualifier — "the text this cell HOLDS, or nothing" beside an `AsText` that means only "what this cell SAYS" — so `IsText` falls out as "own text is not null", the matcher is one call, and the two members cannot disagree. No new power; a contract that says what it means, and the kind of wart that is free to fix in an alpha and permanent after 1.0. Unsettled: the name (`Text` collides with the spreadsheet vocabulary's asserting `p.Text()`; `OwnText`/`HeldText`/`TextOrNull` all work and none is good). Mechanical and wide: `ISpace`, `Point`, two implementations, the matchers, `GridSpace.Create(..., isText:)`, ~77 test references; every existing matcher test should pass untouched, which is the check that it was a pure reshaping. Removing the fact outright instead would cost either a behaviour change (`Containing` becomes what `Saying` is, so `RowContaining("2024")` finds a numeric 2024) or a naming problem (a backend cannot re-declare `RowContaining` with the core's signature — two `using static` imports would be ambiguous).
  - **Why text and not numbers.** A question belongs on `ISpace` only if every conceivable space can answer it meaningfully AND code that names no space needs it. Text passes both: the STRUCTURE of a document is written in it (captions, labels, headings), which is what the generic matchers look for. Numbers fail the first — whether a CSV's "42" is a number is a backend's decision — and are data, read by code that already names its space (`p.Kind() == CellKind.Number`). So a future `IsNumber` is a request for a typed predicate until someone shows space-agnostic code that needs it; a second per-kind member, boolean or own-value, is the kind set creeping back into Core a member at a time, and would be the signal to go generic or stay out, never to add one.
  - **(2) A uniform way to ask a cell for ANY of its facets — large, parked.** A cell does not map to one value: it maps to a value (of one of several kinds), a formula (a string), a font colour, a fill, whether it is merged. The generic spellings tried and what broke them: `Holds<TValue>(value, comparer)` — attractive (kind knowledge stays in the backend, the matching policy stays above it in the caller's comparer, a yes/no that never hands a value back and so stays clear of the leaf firewall), but it must mean the cell's VALUE and never a facet: `Holds("SUM(A1)")` cannot say value or formula, `Holds(CellColor.Red)` cannot say font or fill, and a facet answered through it breaks honest absence (a space that never read its formulas would compile and answer "no"); also a kind is not a CLR type — "Number" is `decimal`, `double` and `int`, so `Holds<decimal>()` and `Holds<int>()` could disagree — and generic interface dispatch per cell is unmeasured. `Option<TKind> IsKind<TKind>(point)` — the owner's, and the owner's own objection: a formula is not a type, it is a SECOND STRING a point in a spreadsheet space maps to, so a type cannot be the index. What would work is a KEY that names the facet and carries its result type and the space it demands — `Facet<TSpace, T>`: `Cells.Text`, `Sheet.Formula`, `Sheet.FontColor` — which keeps the demand at compile time; but that is exactly what `p.Formula()`, `p.Font()`, `p.Kind()` already ARE (a typed accessor with its demand in its constraint, owned by the backend that owns the facet), reified. What reifying buys is real and is this project's own test — PREDICATES AS DATA: `Where(Sheet.FontColor, Is(Red))` can be inspected, shown in a dry run and run backward by a writer, where `p => p.Font().Color == Red` is opaque code. A design with wide reach over every matcher and rule, wanted by nothing today; it starts from here, and not by editing `ISpace`. **The owner's image, a night later (2026-09-21), and why it is cheaper than it first sounded:** a point is an ADDRESS, not a value — something you can turn over in your hand and look at from different angles, asking whether it has this facet or that — which is already how the library treats it (`Point` compares by address, and every read on it is an extension some backend contributes); facets would make that explicit. And they need NOT touch `ISpace`: a facet key is the existing typed read turned into a value, so facets can be an ADDITIVE layer over what ships — a small `Facet<TSpace, T>`, the existing reads offered as facet values beside their method forms, matcher overloads taking a facet and a condition — with `IsText` untouched (or simply exposed as `Cells.Text`), nothing broken, and removable if wrong. What it buys is a declaration that can describe its own conditions: `RowsWhileAny(Sheet.FontColor, Is(CellColor.Red))` where today the engine holds an opaque function — so a dry run and a failure can SAY the condition, a writer can run it backward, and a condition can be checked against a space before a file is opened. For the session: `Option<T>` means "this cell has none", never "this space never looked" (the `TSpace` in the key keeps that a compile error); a small CLOSED condition vocabulary (`Is`, `In`, `Matches`, `And`, `Or`) so conditions stay writer-executable, with the lambda kept as the escape hatch; whether kinds are facets (`Cells.Number`), which touches the leaf firewall; each backend owns its facets. **Shape agreed in conversation (owner, 2026-09-21), still unbuilt:** the read is `bool TryGetFacet<TSpace, TResult>(this Point<TSpace> point, IFacet<TSpace, TResult> facet, out TResult value)` — `TryX(out)`, the .NET idiom and the shape `ICellSpace.DecimalAt(out value, out problem)` already has, NOT an `Option<T>` (none exists here or in netstandard2.0, and no option algebra is expected); a facet is looked up by a KEY, never by a type (`GetFacet<decimal>` cannot say which of two strings is meant); the key is an interface contravariant in its space, `IFacet<in TSpace, TResult>`, as the typed landmarks and strategies are, so a facet declared ONCE at the narrowest space that can answer it (`Cells.Decimal` over `ICellSpace`) serves every space that offers more and refuses to compile over one that offers less (`Sheet.Formula` over a plain sheet); keys keep their qualifier (`Cells.`, `Sheet.`) — a consumer writes `Decimal()` and meets the key only in the condition form, and a bare `Decimal` facet beside a `Decimal()` leaf under two `using static` imports is the ambiguity that two `RowContaining`s would be; and a leaf ASSERTS where a facet ASKS — `Decimal()` fails with a located sentence in the document's vocabulary, and the reason for a miss (kind versus conversion) is a `CellProblem` a bare bool cannot carry — so in a first cut the facet WRAPS the existing read rather than the leaf being rebuilt over the facet, and nothing in the algebra changes. The spike that would let it be judged, five pieces and no more: the interface with `TryGetFacet`/`HasFacet`; three or four facets in the spreadsheet package over existing reads; one condition value (`Is(CellColor.Red)`); ONE matcher overload taking a facet and a condition; and the payoff shown — the dry run and a failure saying "rows while font colour is Red", and the same declaration refusing to compile over a sheet that never read its formatting. More interesting than the labels session, less urgent; not to be started without the owner's word.

## Example Usage

The linqpad scripts below are written in the tree's own vocabulary and reference the built
`Unrect.Engine.dll` beside the others, since `Map`/`Apply`/`MapWithDiagnostics` live there: a
declaration file imports `using static Unrect.Projections.ProjectionBuilders<TSpace>;` plus a
backend's own closed vocabulary (`SheetProjectionBuilders<TSpace>` or
`SpreadsheetProjectionBuilders<TSpace>`) once — the workbook scripts all name the FULL space,
`ISpreadsheetSpace` with `SpreadsheetProjectionBuilders`, opened by `CreateWithFormulas`, because a
script copied from one should start where `.Font()` and `Formula()` compile (a declaration's space
is fixed by those imports, not by how the workbook is opened: the owner's first `.Font()` failed to
compile over `ICellSpace`, reported as a `Column` overload not found) — a cell read is `point.Decimal()`/`.Text()`/…
or the canonical `point.AsText()`/`point.Value()`, and a table read by name is
`row["Amount"].Decimal()` rather than an accessor on a value the view used to hand back directly.

- `linqpad/simple-report.linq` — parses `examples/simple-report.xlsx`: a header flow of typed leaves over `Table<Transaction>()` (the reflective rung) with the two demonstration caption overrides; table defaults absorb the blank gap and header row. Zero point-level accessor calls — the reflective binder does the reading.
- `linqpad/investors-by-deal.linq` — parses `examples/investors-by-deal.xlsx`: one deal-block `VerticalFlow` (`Text()` over `Table<DealTransaction>()`), applied with `VerticalRepeat(deal)` — the gaps between deals need nothing said. All six captions bind with nothing declared.
- `linqpad/investor-summary.linq` — the reference report (`examples/investor-summary.xlsx`), and the corpus's one worked example of the lambda table form: its two tables keep their `Table(r => …)` spelling, where `r` is a `TableRow<ISpreadsheetSpace>` and a cell read is `r["Weight"].Decimal()`; its discovered `Column(c => …)` header is left alone, plus a nested `VerticalRepeat` of per-investor blocks (`atLeast: 1`) and the post-parse correlation check.
- `linqpad/investor-irr.linq` — `examples/investor-irr.xlsx`: the `Heading`/`.Of`/`.Until` demonstration, unchanged in spelling. Two heading-separated series of the same per-investor blocks, parsed by ONE `VerticalRepeat` declared once and placed twice.
- `linqpad/array.linq` — shapes over an in-memory 2D integer array with `GridSpace.Create(nums, isBlank: v => v == 0)` (now a `GridSpace<int>`, i.e. `IValueSpace<int>`): `VerticalRepeat(block)` over a `VerticalFlow` of `Row` then `Range`, with each cell read as `point.Value()` rather than through a `CellValue` accessor — the example that shows the vocabulary is not Excel-specific, nor tied to a kind vocabulary at all.
- `linqpad/edge-cases.linq` — `examples/edge-cases.xlsx`: an error cell end-to-end via `point.IsError()`/`.ErrorText()`, a script-side `Reads(p)` that asks the `Is…()` questions in the order it cares about (there is no "kind" to ask for), whitespace-vs-empty-vs-absent blankness under `IsBlank`/`IsText`, how blankness changes discovered extents, `RowSaying`/`ColumnSaying` finding a row by what a cell *renders* rather than what it holds, and a section printing the kinded leaves' kind-vs-conversion diagnostic sentences via `CellProblem`.
- `linqpad/multi-header-table.linq` — `examples/multi-header-table.xlsx`: a header two rows tall (merged "From"/"To" over `Id | Code | Id | Code`, the sheet indented a row and a column). Dumps the column paths, reads by path (`r["From", "Id"]`, `r["To", 1]`), then binds a flat `Transfer(int FromId, …)` with `Table<Transfer>(2)` and nothing declared.
- `linqpad/scrubbed-k1.linq` — parses the LOCAL-ONLY `examples/scrubbed-k1.xlsx` (gitignored; script fails without it): an `Overlay` header that digests itself into `{Entity, AtaxColumn, Columns}` by resolving fund columns from content (the entity card declared via `Fields`, an `IReadOnlyDictionary<string, Point<ISpreadsheetSpace>>`), one `section` shape placed twice via `Heading(...).Of(section)`, and a fund-centric pivot validated by `AllAllocationsSumToFederal`. The unconsumed-space `Info` doubles as the campaign burn-down.
